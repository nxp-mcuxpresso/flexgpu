1 About This Document
=====================

1.1 Scope
---------

This driver implements VeriSilicon's Vivante VGLite vector graphics API,
version 3.0, on the NXP FlexGPU. The API is defined by VeriSilicon:
``vg_lite.h`` is the VeriSilicon public header and keeps its original copyright
and license notice. ``vg_lite_ext.h`` and the driver sources are NXP.

The driver implements the raster part of the VGLite API. Surface allocation,
image blits, rectangle clears, compositing, scissoring, mask layers, colour
transformation and dithering are hardware accelerated. Vector path
construction, path rendering, gradient paints, stroking and pattern fills are
not supported.

The driver exposes one image processing pipeline. A frame is built by writing
into a render target with a sequence of operations: vg_lite_clear fills a
rectangle with a constant colour, vg_lite_blit and vg_lite_blit_rect transform
an image and composite it, vg_lite_copy_image moves a region without resampling
it, and the state calls around them select the blend equation, the global alpha
handling, the colour keys, the colour transformation, the scissor rectangles
and the mask layer that apply to the following operations. Work is queued and
submitted as a batch, so an application builds a frame with many calls and then
synchronises once with vg_lite_finish.

This manual documents the entry points this driver supports, grouped by
purpose, with the description of what each one does, its prototype, its
parameters and its return values, together with the data types they use.
Section 2 describes the limitations that apply to operations which are
supported but behave differently from what the VGLite specification prescribes.
Appendix D lists, in one place, the entry points, the data types and the
silicon features that the public headers declare but this driver does not
support.

2 Limitations
=============

The operations below are supported and execute on the GPU, but the result
differs from what the VGLite specification leads an application to expect, or a
specific argument combination cannot be performed. The function reference
points at the entries of this chapter from every affected entry point. Entry
points that are not supported at all are a separate matter and are listed in
Appendix D.


2.1 Blending is computed in a linear colour space
-------------------------------------------------

The GPU converts every input to linear light before blending, applies the blend
equation there, and then applies the gamma function to the result if the render
target format carries gamma. The VGLite specification expects the blend to be
computed in the colour space of the destination, with a gamma conversion only
when an input colour space differs from the destination colour space. The two
orders of operation do not commute, so the resulting colours differ from the
expected ones.

With the OpenVG pixel formats the behaviour is as expected, because those
formats state their colour space explicitly: the ``OPENVG_s*`` formats are sRGB
and the ``OPENVG_l*`` formats are linear RGB. A linear RGB render target is the
case the hardware handles most directly, since the destination is already
linear and the blend is computed in linear light.

With the VGLite pixel formats the result differs, because those formats are
treated as sRGB, that is as carrying gamma. Any blend into a VGLite format
target is therefore computed in linear light and converted back, which is not
what the specification prescribes. Use the OpenVG formats where the exact blend
result matters.

2.2 Non-linear grayscale formats cannot be converted
----------------------------------------------------

The inverse gamma stage of the GPU does not convert a non-linear grayscale
value to linear light. A grayscale format that carries gamma can therefore not
be used where the pipeline has to linearise it, and the GPU asserts if such a
format reaches it.

The affected formats are the ones the driver maps to a gamma carrying
grayscale: ``VG_LITE_L8`` and ``OPENVG_sL_8``, together with the 1-bit
``OPENVG_BW_1``. The linear grayscale formats ``OPENVG_lL_8`` and
``VG_LITE_L16`` are not affected.

The driver checks the input format and returns ``VG_LITE_NOT_SUPPORT`` instead
of letting the operation reach the GPU, so an application sees a clean error
rather than an assert.

2.3 VGLite blend modes are computed premultiplied
-------------------------------------------------

The GPU implements the OpenVG Porter-Duff blend equations. Every VGLite blend
mode has a Porter-Duff equivalent, but with one fundamental difference: the
Porter-Duff equations are defined on premultiplied colour, while the VGLite
modes are defined on the colour as it is stored, premultiplied or not.

The GPU always premultiplies the source and the destination before it evaluates
the equation. A ``VG_LITE_BLEND_*`` mode applied to non-premultiplied content
therefore produces a different result from the one the VGLite specification
describes; the effect is most visible on the modes that are not a plain
``SRC_OVER``, such as darken, lighten, multiply and screen.

Use the ``OPENVG_BLEND_*`` modes, which state premultiplication explicitly,
when the exact blend result matters.

2.4 A YUV source cannot be converted into a linear RGB target
-------------------------------------------------------------

When the source buffer is a YUV format, the hardware always applies the gamma
function to the output, so the result is sRGB. Gamma correction cannot be
suppressed for a YUV source, and a linear RGB render target therefore receives
sRGB values.

Workaround: perform the conversion in two steps. First convert the YUV source
into an sRGB target, then convert that sRGB buffer into the linear RGB target.

2.5 Driver Scope
----------------

The following properties of this driver build are not defects but boundaries of
the delivery.


1. The driver targets 32-bit FreeRTOS only.
2. Mask fill and mask clear operations are performed on the CPU and are not hardware accelerated.
3. When a projective transformation is active, at most 3 scissor rectangles are honoured instead of 4.
4. vg_lite_flush can block while the command/copy DMA is still active.
5. A graphics buffer that is still being consumed by the GPU can be modified by a concurrent CPU side API call. The application owns the synchronisation.

4 Function Reference
====================

Functions are grouped by purpose. Each entry gives a description of what the
function does, the prototype taken from the shipped header, a parameter table
and the possible return values. Where a limitation of Section 2 applies, the
entry points at it.


4.1 Context Control
-------------------

These functions create and tear down the implicit driver context and control
how work is submitted to the GPU. vg_lite_init must be called before any other
entry point. It may be called more than once, and only the first call
configures the driver. No other entry point may be used after vg_lite_close
until the context is initialized again.


.. list-table::
   :widths: 100
   :header-rows: 1

   * - Entry point

   * - ``vg_lite_init``
   * - ``vg_lite_close``
   * - ``vg_lite_flush``
   * - ``vg_lite_finish``
   * - ``vg_lite_frame_delimiter``
   * - ``vg_lite_set_command_buffer_size``
   * - ``vg_lite_set_command_buffer``
   * - ``vg_lite_irq_handler_ext``

vg_lite_init
~~~~~~~~~~~~

**Description:**

Creates the implicit driver context and brings the GPU up. The call powers and
resets the hardware, reads the silicon identity and builds the feature table
that vg_lite_query_feature answers from, creates the shared memory pool that
GPU visible allocations are taken from, and prepares the command queue that
every later call appends to. The shared memory pool is located through the
``_shmem_pool_base`` and ``_shmem_pool_size`` symbols, which the linker script
of the platform must define; see Section 1.5. The tessellation window arguments
are accepted for source compatibility and are ignored by this driver. There is
one context per driver instance, and vg_lite_init may be called more than once:
the driver records that it is configured, so a call made while it already is
returns ``VG_LITE_SUCCESS`` at once, without configuring the hardware again and
without allocating anything. This is the normal sequence on FlexGPU. The window
setup code of the platform calls vg_lite_init first, because
vg_lite_wrap_buffer_ext needs an initialized driver to wrap the frame buffers,
and the application then calls vg_lite_init again as part of its own VGLite
initialization, as it does on every VGLite platform. Because a repeated call
returns early, a setting that only takes effect at initialization, such as the
size passed to vg_lite_set_command_buffer_size, must be made before the first
call. The calls are not counted: a single vg_lite_close shuts the driver down,
however many times vg_lite_init succeeded. No other entry point may be called
before the first vg_lite_init.

**Syntax:**

.. code-block:: c

   vg_lite_error_t vg_lite_init(
       vg_lite_uint32_t tess_width,
       vg_lite_uint32_t tess_height);

**Parameters:**

.. list-table::
   :widths: 18 28 54
   :header-rows: 1

   * - Parameter
     - Type
     - Description

   * - ``tess_width``
     - ``vg_lite_uint32_t``
     - Width of the tessellation window in pixels. Accepted for source compatibility and ignored by this driver.
   * - ``tess_height``
     - ``vg_lite_uint32_t``
     - Height of the tessellation window in pixels. Accepted for source compatibility and ignored by this driver.

**Returns:**

- ``VG_LITE_SUCCESS`` if the function succeeds.
- Any other ``vg_lite_error_t`` value on failure. See Section 3.2.


vg_lite_close
~~~~~~~~~~~~~

**Description:**

Destroys the context created by vg_lite_init, waits for outstanding GPU work to
retire, releases the driver resources and powers the GPU down. Calls to
vg_lite_init are not reference counted, so one vg_lite_close shuts the driver
down even when vg_lite_init was called several times, for example once by the
window setup code and once by the application. Call it once, after the last
user of the driver is done. A later vg_lite_init initializes the driver again.

**Syntax:**

.. code-block:: c

   vg_lite_error_t vg_lite_close(void);

**Parameters:**

This function takes no parameters.

**Returns:**

- ``VG_LITE_SUCCESS`` if the function succeeds.
- Any other ``vg_lite_error_t`` value on failure. See Section 3.2.


vg_lite_flush
~~~~~~~~~~~~~

**Description:**

Closes the command buffer that the preceding calls filled and submits it to the
GPU, then returns without waiting for the work to finish. Use it to overlap CPU
work with GPU execution: build the next frame while the current one renders.
The render target must not be read by the CPU, and the source buffers must not
be modified, until the work has retired; use vg_lite_finish, or poll
``VG_LITE_GPU_IDLE_STATE`` through vg_lite_get_parameter, to establish that.

**Syntax:**

.. code-block:: c

   vg_lite_error_t vg_lite_flush(void);

**Parameters:**

This function takes no parameters.

**Returns:**

- ``VG_LITE_SUCCESS`` if the function succeeds.
- Any other ``vg_lite_error_t`` value on failure. See Section 3.2.


vg_lite_finish
~~~~~~~~~~~~~~

**Description:**

Submits the pending command buffer and blocks until the GPU has retired all of
it. After a successful return the render target holds the finished result and
can be read by the CPU, and every source buffer the submitted work referenced
may be modified or released again. This is the synchronisation point an
application uses before it hands a buffer to a display controller or to another
processing stage.

**Syntax:**

.. code-block:: c

   vg_lite_error_t vg_lite_finish(void);

**Parameters:**

This function takes no parameters.

**Returns:**

- ``VG_LITE_SUCCESS`` if the function succeeds.
- Any other ``vg_lite_error_t`` value on failure. See Section 3.2.


vg_lite_frame_delimiter
~~~~~~~~~~~~~~~~~~~~~~~

**Description:**

Marks a frame boundary in the command stream. The driver submits a dedicated

zero stall flag submits and waits for the GPU to go idle, like vg_lite_finish.
The frame flag argument is accepted for source compatibility and does not
change the behaviour.

**Syntax:**

   * - ``stall_flag``

     - Non-zero to wait for GPU completion, zero to only submit.

4.3 Pixel Buffer Management
---------------------------

A pixel buffer is described by a vg_lite_buffer_t and can act as a render
target, as a blit source, as a pattern, or as a mask layer. The driver enforces
the format specific stride and base address alignment that the GPU requires, so
applications should always let the driver compute the stride instead of
assuming one.


.. list-table::
   :widths: 100
   :header-rows: 1

   * - Entry point

   * - ``vg_lite_allocate``
   * - ``vg_lite_free``

   * - ``vg_lite_enable_dither_ext``
   * - ``vg_lite_disable_dither``
   * - ``vg_lite_set_gamma``

vg_lite_allocate
~~~~~~~~~~~~~~~~

**Description:**

Allocates GPU accessible memory for the surface the caller describes. The
width, height and format fields of the descriptor must be set before the call;
the driver derives the stride and the base address alignment the hardware
requires for that format, allocates from the shared memory pool, and fills in
the stride, the CPU pointer, the GPU address and the handle. For a multi plane
YUV format the chroma and alpha planes are placed inside the same allocation
and their pointers are filled in as well, so one allocation backs the whole
surface. An unknown or unsupported format is rejected with
``VG_LITE_NOT_SUPPORT`` before anything is allocated. The resulting buffer is
driver owned and is released by vg_lite_free.

**Limitation:** Non-linear grayscale formats cannot be converted. See Section
2.2.

vg_lite_upload_buffer
~~~~~~~~~~~~~~~~~~~~~

**Description:**

Copies planar pixel data from application memory into an already allocated
buffer, converting the per plane stride as needed. This is the normal way to
populate a YUV surface. Before it writes anything, the driver adds up the bytes
the plane geometry of the destination requires and checks that they fit inside
the recorded capacity of the buffer, so a descriptor whose geometry outgrows
its memory is rejected with ``VG_LITE_INVALID_ARGUMENT`` rather than
overrunning the allocation. The destination must therefore be a buffer the
driver knows the size of, that is one from vg_lite_allocate, or one wrapped
with vg_lite_wrap_buffer_ext and its true size.

**Limitation:** Non-linear grayscale formats cannot be converted. See Section
2.2.

**Syntax:**

.. code-block:: c

   vg_lite_error_t vg_lite_upload_buffer(

vg_lite_upload_buffer_ext
~~~~~~~~~~~~~~~~~~~~~~~~~

**Description:**

Copies pixel data into an already allocated buffer, with support for up to four

differs from the destination; only the destination plane width is copied per
row. A source stride of 0 means that plane is tightly packed, in which case the
destination plane stride is used. The copy is bounded the same way as in
vg_lite_upload_buffer: the bytes the destination geometry requires must fit the
recorded capacity of the buffer, otherwise the call reports
``VG_LITE_INVALID_ARGUMENT`` before writing. The caller allocates and releases
the destination memory.

**Limitation:** Non-linear grayscale formats cannot be converted. See Section

vg_lite_wrap_buffer_ext
~~~~~~~~~~~~~~~~~~~~~~~

**Description:**

Wraps a caller owned memory block into a vg_lite_buffer_t without copying it.
The caller fills in the buffer property fields (width, height, stride, format
and the YUV details) and keeps the ownership of the memory. The driver must
already be initialized, because the GPU address of the block is resolved
through the shared memory space that vg_lite_init creates. This is why the
window setup code of a platform calls vg_lite_init itself before it wraps the
frame buffers, ahead of the application's own vg_lite_init; the second call is
harmless. The size argument declares how many bytes are readable and writable
at that address: the driver cannot discover the length of an allocation it did
not make, so the declared size becomes the recorded capacity of the buffer and
is what bounds later writes such as vg_lite_upload_buffer. It must therefore be
the true size of the allocation; a size of 0, or one too small for the geometry
in the descriptor, is rejected with ``VG_LITE_INVALID_ARGUMENT``. Use
vg_lite_unwrap_buffer_ext before the memory is freed.

**Limitation:** Non-linear grayscale formats cannot be converted. See Section
2.2.

**Syntax:**

.. code-block:: c

   vg_lite_error_t vg_lite_wrap_buffer_ext(
       vg_lite_buffer_t *buffer,

**Parameters:**

.. list-table::
   :widths: 18 28 54

     - Type
     - Description

     - Buffer descriptor operated on.
   * - ``user_buffer``
     - ``vg_lite_void *``
     - Caller owned backing memory to wrap.
   * - ``user_buffer_size``
     - ``vg_lite_uint32_t``
     - Number of bytes that are readable and writable at ``user_buffer``. The driver cannot discover the length of an allocation it did not make, so the caller must declare it. The value becomes the recorded capacity of the buffer and is what bounds later writes such as vg_lite_upload_buffer, so it must be the true size of the allocation. The call fails with VG_LITE_INVALID_ARGUMENT when the size is 0, or when it is too small for the geometry described by buffer.

4.5 Blit and Compositing
------------------------

Blit operations move and transform rectangular pixel data into the render
target while applying a blend equation. They form the raster part of the API
and do not need a tessellation buffer.

vg_lite_clear
~~~~~~~~~~~~~

**Description:**

Fills a rectangle of the render target with a constant colour, with no source

the cheapest write the pipeline offers and it is the primitive an application
uses to implement a filled rectangle: a rectangle fill is a clear restricted to
that rectangle. Several clears with different rectangles and colours compose
the flat coloured parts of a frame without any path rendering.

vg_lite_blit
~~~~~~~~~~~~

**Description:**

Transforms a whole source image by the supplied matrix and composites it into
the render target. This is the central operation of the raster pipeline. The
matrix may be a translation, a scale, a rotation, any affine combination of
those, or a projective transformation; the filter argument selects the sampling
quality, where ``VG_LITE_FILTER_BI_LINEAR`` gives the best result,
``VG_LITE_FILTER_LINEAR`` is faster, and ``VG_LITE_FILTER_POINT`` samples
without interpolation. The blend argument selects how the transformed source is
combined with the target content, and the colour argument feeds the paint
colour that the image mode of the source buffer mixes in, so that a single blit
can tint, multiply or stencil the image. A null matrix is treated as the
identity.

**Limitation:** Blending is computed in a linear colour space. See Section 2.1.

**Limitation:** VGLite blend modes are computed premultiplied. See Section 2.3.

**Limitation:** Non-linear grayscale formats cannot be converted. See Section
2.2.

**Limitation:** A YUV source cannot be converted into a linear RGB target. See
Section 2.4.

**Syntax:**

.. code-block:: c

   vg_lite_error_t vg_lite_blit(
       vg_lite_buffer_t *target,

   * - ``source``
     - ``vg_lite_buffer_t *``
     - Source image that is sampled.
   * - ``matrix``
     - ``vg_lite_matrix_t *``

Appendix C Minimal Usage Example
================================

The sequence below only uses entry points that are supported.


.. code-block:: c

   #include "vg_lite.h"

   static vg_lite_buffer_t target;
   static vg_lite_buffer_t source;

   /* 64 x 64 RGBA8888 image to blit, filled in by the application. */
   static vg_lite_uint8_t source_pixels[64 * 64 * 4];

   vg_lite_error_t render_once(void)
   {
       vg_lite_error_t  err;
       vg_lite_matrix_t matrix;

       /* 1. Create the context. The tessellation window arguments are
        *    ignored by this driver. */
       err = vg_lite_init(0, 0);
       if (err != VG_LITE_SUCCESS) {
           return err;
       }

       /* 2. Describe and allocate the render target. The driver fills in the
        *    stride and the addresses. */
       target.width  = 480;
       target.height = 272;
       target.format = VG_LITE_BGRA8888;
       err = vg_lite_allocate(&target);
       if (err != VG_LITE_SUCCESS) {
           goto done;
       }

       /* 3. Clear the whole target. */
       err = vg_lite_clear(&target, NULL, 0xFF202020);
       if (err != VG_LITE_SUCCESS) {
           goto free_target;
       }
       /* 3b. Allocate the source image and copy the pixels into it. */
       source.width  = 64;
       source.height = 64;
       source.format = VG_LITE_RGBA8888;
       err = vg_lite_allocate(&source);
       if (err != VG_LITE_SUCCESS) {
           goto free_target;
       }
       {
           vg_lite_uint8_t  *planes[3]  = { source_pixels, NULL, NULL };
           vg_lite_uint32_t  strides[3] = { 64 * 4, 0, 0 };

           err = vg_lite_upload_buffer(&source, planes, strides);
           if (err != VG_LITE_SUCCESS) {
               goto free_source;
           }
       }

       /* 4. Build a transformation. */
       vg_lite_identity(&matrix);
       vg_lite_translate(100.0f, 60.0f, &matrix);
       vg_lite_rotate(15.0f, &matrix);

       /* 5. Raster rendering: transform the source image and composite it
        *    into the target. */
       err = vg_lite_blit(&target, &source, &matrix,
                          VG_LITE_BLEND_SRC_OVER, 0, VG_LITE_FILTER_BI_LINEAR);
       if (err != VG_LITE_SUCCESS) {
           goto free_source;
       }

       /* 6. Submit and wait, then the CPU may read the target. */
       err = vg_lite_finish();

   free_source:
       vg_lite_free(&source);
   free_target:
       vg_lite_free(&target);
   done:
       vg_lite_close();
       return err;
   }
